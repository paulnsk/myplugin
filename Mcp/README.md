# ProjectStudio BIM MCP — первый выпуск

23.10.2026: код перенесён в отдельный MyPlugin.sln. Описание ниже сохраняет техническую историю
встроенной версии; регистрация, пути ресурсов и поставка адаптируются для плагина.
Текущее состояние — ../Notes/ПЕРЕНОС_В_ПЛАГИН.md, краткие возможности — ../README.md.
Общая часть больше не компилируется в CAE.Project; электрический адаптер — в ../Electrica.

## Принципы API

- Схемы простые и однозначные для слабых моделей: один формат действия, понятные поля, без языка программирования и лишних вариантов.
- Схемы, ответы и инструкции короткие по трафику: не дублировать определения и данные; подробности — по запросу. При изменении API измерять размеры tools/list, инструкций и типовых ответов до тестов внешними моделями.
- Пока нет внешних потребителей, неверные решения удаляем, а не сохраняем ради гипотетической совместимости.
- Инструкции — спокойные конструктивные подсказки, не набор категоричных запретов. Примеры показывают форму запроса, не ограничивают объём задания; модель может самостоятельно продолжать согласованную работу пакетами.
- Корневая инструкция продукта — короткое оглавление направлений. Детали загружаются тематическими help_read по задаче; help_list без prefix показывает только корни, с prefix=electrica — темы электрики. Такой подход сохраняется для следующих продуктов.
- Существующие бизнес-алгоритмы не копируем/не извлекаем. Публичные API вызываем напрямую, согласованные приватные входы изолированы в ElectricaPrivateOperations; сигнатуры проверяются при регистрации.

## Запуск

1. Собрать продукт обычным способом и запустить nanoCAD вручную.
2. Выполнить `CW_MCP_START`. В CAD-консоли появятся endpoint, путь JSON настроек подключения и путь лога.
3. Передать клиенту URL из `connection-<PID>.json` в каталоге `runtimeDirectory` из `settings.json`. Авторизация не требуется: сервер слушает только `127.0.0.1`.
4. Начать с `app_context`, `help_list`, `help_read` с `name=platform`. Скилы лежат здесь же в `Skills/`, устанавливать их глобально необязательно.
5. Остановить командой `CW_MCP_STOP`.

Настройки — `settings.json` рядом с исходниками MCP: `port`, `logging`, `runtimeDirectory`. По умолчанию URL `http://127.0.0.1:19426/mcp/`, runtime/логи в `C:\tests\ProjectStudioMcp\runtime`; `logging=false` отключает лог в любой сборке. Конфиг читается при `CW_MCP_START`: после его изменения достаточно STOP/START без пересборки. Старые файлы runtime не переносятся и не удаляются. Скилы и конфиг пока находятся относительно исходной папки (CallerFilePath): это локальная разработка, не готовый инсталлятор. Измерительные скрипты читают тот же конфиг.

Транспорт: MCP JSON-RPC через stateless Streamable HTTP, ответы JSON. GET/SSE не поддерживаются (405); POST notifications — 202. Версии 2025-03-26, 2025-06-18, 2025-11-25. Инструменты обнаруживаются через tools/list. Любой локальный процесс может управлять CAD через этот endpoint; наружу он не опубликован. Проверка Origin отсекает обращения с посторонних веб-страниц.

В Codex сервер зарегистрирован как `projectstudio-bim`, без токена и дополнительных заголовков. Скилы написаны по-русски и приходят через `help_read` полным текстом; подсказки в initialize и базовых инструментах объясняют, откуда начать. Харнессу нужно передавать модели поле `instructions` из initialize и описания инструментов.

Графический MCP Inspector запускается командой `npx @modelcontextprotocol/inspector` (нужен Node.js). Он открывает свой интерфейс в браузере, отдельный от нашего сервера. Выбрать Streamable HTTP, указать `http://127.0.0.1:19426/mcp/`, подключиться и открыть список Tools. Вкладка `help_read` с `{"name":"platform"}` возвращает начальную инструкцию. Отдельный инсталлятор или глобальная установка npm не нужны.

## Проверка

Совместный прогон — проверка глазами обычного MCP-клиента: агент использует только API и выдаваемые им инструкции. Исходники не подменяют недостающую справку. Читать их допустимо для расследования уже обнаруженного сбоя/пробела; найденную причину и необходимую подсказку затем фиксируем в MCP, а не оставляем тайным знанием агента.

`Tests/Test-McpElectrical.ps1 -ConnectionFile <JSON>` дополнительно проверяет электрические инструменты, аннотации мутаций, тематическую справку и размер каталога. `-CreateSample` разрешает создать новый тестовый проект и проверить Ки/прокладку/кабельные изделия/аппараты/питание/электрический расчёт/редактирование проектной БД. Нужны демонстрационные базы с ARS/R418 и электротехническими изделиями. Сценарий подготовлен, новый runtime-прогон ещё не выполнен.

`Tests/Test-Mcp.ps1 -ConnectionFile <полный путь к connection JSON>` проверяет handshake, discovery, справку, ошибки и безопасность, не изменяя CAD-проект. С `-CreateElectricalSample` создаёт новый небольшой электрический проект (по умолчанию в `C:\test\ProjectStudioMcp\<GUID>`), этаж/комнату, два светильника и трассу, читает результат обратно и сохраняет проект. Текущий workspace перед этим должен быть закрыт вручную. Команду запускает агент после запуска nanoCAD пользователем.

Мутации не атомарны. Ошибка возвращает ID созданного/затронутого, когда это известно. Запрос, уже выполняющийся в CAD, не отменяется сетевым таймаутом и не повторяется автоматически. Не редактировать проект параллельно длинному изменяющему вызову. При неизвестном модальном окне заканчивать/отменять операцию вручную, затем смотреть call.executing/call.failed в логе.

### Замеры производительности

При включённом логировании каждый HTTP-запрос получает строку `request.timing` после закрытия ответа. `callId` связывает её с обычным логом вызова, `requestId` — с JSON-RPC-запросом клиента. Ответы клиенту не дополнены диагностикой.

`stagesMs` — последовательные интервалы по монотонному Stopwatch: чтение/разбор запроса, подготовка вызова, очередь CAD, проверки, вход в команду, инструмент, выход из команды, подготовка JSON-результата и конверта, сериализация, запись/закрытие ответа. У запросов без CAD соответствующие этапы отсутствуют. При ранней ошибке последняя отметка включает незавершённую работу с предыдущей отметки — читать её вместе с ошибкой. `responseBytes` — размер реально сериализованного тела, без повторной сериализации для замера.

`netLoadMs` — создание и загрузка сети внутри инструмента, `logMs` — существующие записи лога внутри запроса; это **вложенные расходы**, их нельзя прибавлять к сумме этапов. Сама завершающая строка `request.timing` не включена в свой замер. Серверное время начинается после получения запроса из HttpListener и не доказывает скорость всего клиентского пути.

`Tests/Measure-Mcp.ps1` обращается к уже запущенному серверу, ничего не создаёт и не меняет. Измеряет initialize, ping, каталог, справку, статус, контекст и поиск типов; показывает первый и повторные вызовы отдельно, сохраняет клиентские времена и размеры в `runtimeDirectory/client-timing-<GUID>.json`. Серверный лог сопоставляется по requestId. Для проверки загрузки сети нужен отдельный read-only вызов объектов открытого проекта. Билд и запуск nanoCAD делает пользователь; измерительный скрипт запускает агент.

## Границы первой версии

`plan_get_bounds` читает габариты пространства модели через штатный управляемый API nanoCAD (hostmgd/hostdbmgd), локально связанный в MCP без новых ссылок csproj. Возвращает только две точки XYZ в мм, не геометрию чертежа. Габариты включают всё содержимое модели, не только стены; по ним можно создать прямоугольный этаж обычным `contour_create`. Новый путь требует проверки в запущенном CAD после пользовательской сборки.

Обнаружение типов/свойств общее. Поддержаны обычная фабрика точечных объектов, полигональные контуры, маркеры и штатное pairwise-соединение AcadTrace. Продуктовый модуль электрики добавляет Ки/расстановку, прокладку кабелей, назначение изделий, аппараты групп, питание и электрический расчёт. Размещение ещё не гарантирует корректную расчётную сеть/прохождение инженерных проверок. Новые продуктовые операции требуют runtime-прогона; Отопление — следующий продукт. Снимков viewport и универсального исполнения CAD-команд пока нет.

Распределение кода: Protocol — HTTP/каталог/лог; McpCommands — явный lifetime и CAD-thread dispatch; McpCadContext — доступ к текущему проекту; Tools — предметные операции; Skills — единый источник инструкций для файлового доступа и MCP.

## Контекст выполнения CAD

objects_delete принимает items:[{id:...}] и вызывает штатный IAcadObject.Delete с продуктовой обработкой связей/дочерних объектов. waypoints в traces_connect и objects_update задаёт промежуточные точки ломаной; [] выпрямляет трассу. Концы и их привязки сохраняются; для другой пары конечных объектов используются явные удаление и создание. Дуговой маршрут пока не редактируется через waypoints. objects_get.geometry=true возвращает вершины трассы и connectedObjectIds, позволяя проверить геометрию и сохранность связей. Новые проверки включены в Test-Mcp.ps1, требуется пользовательский билд и runtime-прогон.

objects_find возвращает только id/title; nextOffset задаёт следующую страницу, отсутствие означает конец. Подробности — objects_get. objects_create принимает defaults с общими type/dbType/dbId/rotationDegrees/properties; позиция задаётся в каждом items. Поля элемента переопределяют общие, properties объединяются по именам. Возвращённые ID соответствуют порядку items, повторный поиск созданных объектов не нужен.

Ответ инструмента содержит один JSON в content[0].text, без structuredContent-дубля. Создание/изменение возвращает ID, не копию всей карточки. objects_get/database_get: fields выбирает свойства (* — все), objects_get.geometry=true включает вершины; без этих параметров ответ короткий. types_describe поддерживает query/offset/limit (20 свойств по умолчанию). Старые форматы не поддерживаются. Полные размеры нового трафика замеряются после пользовательского билда.

Структура: objects_structure листает прямые children/ports/slaves/parent; objects_add_child вызывает штатный продуктовый компоновщик; ports_connect назначает потребителей порту через общий контракт IPort. Для ElBoard компоновщик добавляет отходящую группу. Это логическая связь, без подбора аппаратов/кабелей или расчёта. Новые операции требуют проверки в CAD; сценарий Test-Mcp.ps1 её содержит. Планы покрытия и работы с реальными проектами — MCP_ПЛАНЫ.md в корне репозитория.

Инструменты выполняются через захваченный WPF Dispatcher потока CAD. Сохраняются checker.StartCommand/EndCommand и блокировки документов; CadCommandСookies/CommandStart не используются, чтобы не запускать общую статистику с принудительным GC. HTTP ожидает Task этой операции. Проверяются занятость CAD и наличие диалога; параллельный CAD-запрос отвергается. Пробная обёртка `CW_MCP_EXECUTE` удалена: её необходимость не была доказана, падение она не устранила.

Исключения инструмента попадают через Task в HTTP-обработчик, логируются как `call.failed` и возвращаются клиенту. Отложенные вызовы, самостоятельно поставленные продуктом через `BeginInvoke`, находятся вне этой границы. Глобального подавления WPF-исключений нет. Профиль `cad.commandEnter`/`cad.commandExit` измеряет оставшиеся checker/блокировки; Stopwatch не создаёт таймеров или фоновых callback. Временные общие GC/Trace-замеры сняты.

Общие точечные операции открывают объекты через пустой Net.OpenObject(id), поиск — через IObjectBankCollection по типу/плану. Полная Net.Load нужна только новым штатным продуктовым алгоритмам расчёта/прокладки; она не добавлена к обычной постановке/чтению объекта. Между HTTP-вызовами нет кэша модельных объектов. После соединителя с собственной сетью и перед очередным изменением снимок сбрасывается. netLoadMs измеряет создание пустых сетей контекста; полная загрузка продуктового алгоритма входит в tool.execute.

objects_get/update, contour_create, traces_connect, objects_structure, objects_add_child и ports_connect принимают только items (1–100 обычных наборов аргументов), даже для одного действия. Схема элемента описана один раз. Выполнение последовательное, одна внешняя блокировка на весь пакет, без транзакционного отката; результат — results в порядке входа. Частичная ошибка возвращает completedResults/failedItemIndex и известные ID ошибочного элемента. У objects_create свой items. objects_update.vertices изменяет любой IAcadContour через SetVertexArray; маркер/CirclePos автоматически не двигаются. После записи вершины проверяются повторным чтением из CAD.
